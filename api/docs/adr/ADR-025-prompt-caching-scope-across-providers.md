# ADR-025: Prompt-Caching Scope Across Providers

**Status**: Accepted
**Date**: 2026-09-06 (updated 2026-09-08 — see "Update, 2026-09-08" below; updated again 2026-09-09 — see "Update, 2026-09-09" below)
**Context**: Audit finding — the same `anthropic.claude-*` model got full prompt caching when called through `anthropic-adapter.ts` but zero caching when routed through `aws-bedrock-adapter.ts`, with no ADR or comment anywhere explaining the inconsistency.
**Related**: `api/src/providers/anthropic/anthropic-adapter.ts`, `api/src/providers/aws-bedrock/aws-bedrock-adapter.ts`, `api/src/providers/openai/openai-adapter.ts`, `api/src/providers/mistral/mistral-adapter.ts`, `api/src/providers/xai/xai-adapter.ts`, `api/src/providers/google/google-adapter.ts`, `api/src/providers/deepseek/deepseek-adapter.ts`, `api/src/providers/vertex-ai/vertex-ai-adapter.ts`, `api/src/providers/cohere/cohere-adapter.ts`, `api/src/providers/azure/azure-openai-adapter.ts`, `api/src/providers/cerebras/cerebras-adapter.ts`, `api/src/providers/databricks/databricks-adapter.ts`, `api/src/providers/byteplus/byteplus-adapter.ts`, `api/src/providers/openai-compatible-hub/openai-compatible-hub-adapter.ts`, `api/src/observability/ci-metrics.ts`, `api/src/services/session-affinity-service.ts`, `api/src/providers/aws-bedrock/__tests__/aws-bedrock-adapter.test.ts`

## Update, 2026-09-08

The five providers this ADR originally flagged as "not yet evaluated" (Google Gemini, DeepSeek, Moonshot/Kimi, Mistral, xAI) have now each been investigated against their real, current API documentation, fetched live on 2026-09-08. Two turned out to have a genuine, implementable per-request control mechanism this repo wasn't using (Mistral, xAI); three turned out to already cache automatically with zero request-side code required (Google Gemini's implicit caching, DeepSeek, Moonshot) — for those three, the real, valuable follow-up was closing the pre-existing "Cache-hit observability is a gap across every provider" negative from the original Consequences section below, at least for the providers whose response `usage` already reports a hit-token count. See each provider's own section for the full citation and reasoning, and see `ci_provider_prompt_cache_tokens_total` (`api/src/observability/ci-metrics.ts`) for the new shared metric this closes that gap with. No provider here got a fabricated mechanism — every claim below cites the exact doc fetched and the exact field/header name confirmed in it.

## Update, 2026-09-09

A follow-up audit swept every adapter this ADR had NOT yet looked at (the original pass only covered Anthropic, OpenAI, Bedrock, and OpenRouter's deliberate exclusion) against each vendor's real, current API documentation, fetched live on 2026-09-09. Nine more real gaps were confirmed and closed: **Vertex AI** and **Cohere** (the two additional examples flagged alongside Bedrock at audit time), plus **Groq**, **Azure OpenAI**, **Cerebras**, **SambaNova**, **Databricks**, and **BytePlus/ModelArk** discovered during the sweep. See each provider's own new section below for the exact citation and mechanism. No provider here got a fabricated mechanism — every claim cites the exact doc fetched and the exact field/header name confirmed in it. (Mistral, xAI, DeepSeek, Google Gemini, and Moonshot/Kimi — the five the original ADR listed as "not yet evaluated" — were closed in the "Update, 2026-09-08" section above.)

## Context

Prompt caching is not one feature with one on/off switch in this codebase — it is a different, provider-native mechanism per provider, wired independently into each adapter (or not wired at all). Before this ADR there was no single place documenting which providers had it, which had been deliberately left out, and which had simply never been looked at. That gap is exactly how the Anthropic-direct/Bedrock inconsistency happened silently: two adapters serving the *same underlying model* (`anthropic.claude-*`), with materially different cost and latency, and nobody had written down that this was known, let alone why.

This ADR is that single place. It is a scope/inventory document, not a design proposal — each section below states what the code actually does today, cites the exact lines, and is explicit about the difference between "evaluated and intentionally out" versus "nobody has checked yet."

A load-bearing piece of context for all provider-native caching (Anthropic, OpenAI, Bedrock): provider-side cache lineage is keyed to a **stable model + stable prefix** served turn-to-turn. Before session/conversation affinity shipped (LOTE AW), 'auto' routing could silently re-select a different model on turn 2 of the same conversation, which meant caching could never hit regardless of what any adapter sent — see `api/src/services/session-affinity-service.ts:1-14`. Every provider section below inherits this dependency; it is not repeated per-provider.

## Decision — current state, per provider

### Have it: Anthropic (direct)

`api/src/providers/anthropic/anthropic-adapter.ts`:
- `convertMessages()` (comment `:695-703`, code `:704-712`) marks the joined system prompt with `cache_control: { type: 'ephemeral' }`.
- `convertTools()` (comment `:801-810`, code `:822`) marks only the **last** tool definition — Anthropic's cache-breakpoint semantics cache everything up to a marked block in a fixed `tools -> system -> messages` order, so marking every tool would be redundant.
- **No minimum-cacheable-size gate.** Both breakpoints are emitted unconditionally, regardless of how short the system prompt or tool list is. Anthropic's own API does not error below its documented minimum (1,024 tokens for most Claude models, more for smaller ones) — it simply doesn't cache — so this is a missed-efficiency gap, not a correctness bug. A separate, already-in-flight fix targets this specific gap; this ADR does not change `anthropic-adapter.ts`.

### Have it: OpenAI

`api/src/providers/openai/openai-adapter.ts:458-476` (non-streaming) and `:605-620` (streaming): sets `prompt_cache_key` to `deriveSessionKey(request)` (`api/src/services/session-affinity-service.ts:134`) on every chat-completion request. OpenAI's prefix cache is automatic server-side; `prompt_cache_key` is OpenAI's own documented mechanism to keep one conversation's cache lineage distinct from a different, differently-keyed conversation that happens to share a prefix. No explicit minimum-size gate is needed here — OpenAI has no equivalent breakpoint marker to conditionally omit; the key is just a stable string.

### Now have it: Mistral — 2026-09-08

`api/src/providers/mistral/mistral-adapter.ts`. Mistral documents `prompt_cache_key` as a chat-completions request field with the SAME contract as OpenAI's field of the same name — "use the same key for requests with shared prompt prefixes ... to increase cache hits" (docs.mistral.ai/studio-api/conversations/advanced/prompt-caching, verified live 2026-09-08). This was a genuine gap, not a deliberate exclusion: Mistral's API is close enough to OpenAI's in most other respects that ADR-025's original pass assumed it lacked any caching control at all, when in fact it mirrors OpenAI's exactly.

- Both `chatCompletion()` and `chatCompletionStream()` now send `prompt_cache_key: deriveSessionKey(request)` — the identical derivation `openai-adapter.ts` already uses, so the two providers' cache lineage keying logic can never drift from each other.
- **No minimum-cacheable-size gate**, matching OpenAI's section above: `prompt_cache_key` is just a stable string, not a breakpoint marker with a request-shape branch to conditionally omit. Mistral's docs do state prompts under 64 tokens never produce a cache hit (their cache blocks are 64 tokens each) — but that is the vendor's own internal eligibility rule, evaluated regardless of what the client sends; there is nothing for this adapter to gate.
- Cache-hit observability: Mistral's response `usage.prompt_tokens_details.cached_tokens` (same nested shape as OpenAI/xAI, confirmed on the same doc page) is now recorded via `recordProviderPromptCacheUsage()` in both the non-streaming response and the streaming path's final usage-bearing chunk.

### Now have it: xAI (Grok) — 2026-09-08

`api/src/providers/xai/xai-adapter.ts`. xAI's prompt cache is automatic server-side, but xAI's own docs (docs.x.ai/developers/advanced-api-usage/prompt-caching/how-it-works, verified live 2026-09-08) document the `x-grok-conv-id` HTTP header as the mechanism to "route requests with the same conversation ID to the same server," maximizing cache hit rate on the standard `/v1/chat/completions` endpoint this adapter uses (a separate `prompt_cache_key` body field applies only to xAI's Responses API, which this adapter does not use — the header is the correct mechanism here, not that field).

- `buildCacheRoutingHeader()` sets `x-grok-conv-id: deriveSessionKey(request)` on both `chatCompletion()` and `chatCompletionStream()` requests — same derivation as OpenAI/Mistral, so all three providers' cache-lineage keys are derived identically even though xAI's transport for it (a header, not a body field) differs.
- Cache-hit observability: xAI's usage object nests the hit count under `prompt_tokens_details.cached_tokens` (confirmed on the same doc page) — recorded via `recordProviderPromptCacheUsage()` in both the non-streaming response and `convertStreamChunk()`'s usage handling. xAI only reports the hit count directly, so the miss count is derived as `prompt_tokens - cached_tokens`.

### Now have it: AWS Bedrock (Claude models) — this ADR

`api/src/providers/aws-bedrock/aws-bedrock-adapter.ts`. Before this change, `git grep cachePoint` returned zero results anywhere in the repository — Bedrock's Converse API has its own real, native caching mechanism (a `cachePoint` content block, not Anthropic-direct's `cache_control` field) that was simply never wired up, for the *same* Claude models `anthropic-adapter.ts` already caches.

What's added:
- `isBedrockClaudeModel()` (`:547`) scopes caching to the Claude family only (Bedrock also hosts Llama, Titan, Mistral, and Nova under the same Converse API — those have their own, different caching contracts and are explicitly out of scope here; see "Not yet evaluated" below).
- `resolveClaudeCacheMinimumTokens()` (`:556`) — **a real, per-model minimum-token gate**, sourced from AWS's own documentation (AWS docs, "Prompt caching for faster model inference", `docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html`, fetched 2026-09-06 — see the `CLAUDE_CACHE_MIN_TOKENS` table at `:510-537` for the full per-model-family list and citation). Unmatched/future Claude model ids fall back to the highest documented minimum (4,096 tokens, `CLAUDE_CACHE_MIN_TOKENS_DEFAULT` at `:538`) — conservative by design: undershooting a real minimum never causes an API error (Bedrock accepts the request and silently skips caching that checkpoint), so the safe direction to be wrong in is "requires more tokens than it actually does," not the reverse.
- `applyClaudeCacheCheckpoint()` (`:588`) places **one** `cachePoint` block at the end of `system` (covering the cumulative `tools` + `system` prefix — Bedrock evaluates the minimum against the combined tokens across sections, processed in a fixed `tools -> system -> messages` order) when a system prompt is present, else one at the end of `tools`. This single-checkpoint placement is AWS's own documented "simplified cache management" recommendation for Anthropic models on Bedrock, not an approximation of Anthropic-direct's two-breakpoint approach — see the file's inline comment block above `CLAUDE_CACHE_MIN_TOKENS` for the full reasoning.
- `buildConverseInput()` (`:623`) is a new shared helper that both `chatCompletion()` and `chatCompletionStream()` now call, replacing what was previously duplicated Converse-input construction in each method. That duplication is very plausibly *how* caching was easy to add to one path and forget on the other in a hypothetical future change — collapsing it removes that specific risk going forward.

Explicitly out of scope for this change: message-content cache checkpoints (e.g., a large per-turn document or image block). Only `tools` and `system` are covered here, matching what `anthropic-adapter.ts` also covers today.

### Now have it: Vertex AI (Gemini) — 2026-09-09

`api/src/providers/vertex-ai/vertex-ai-adapter.ts`. Vertex AI's Gemini models get the SAME implicit context caching, enabled by default for Gemini 2.5+, as the standalone Gemini API — and the SAME response field name, `UsageMetadata.cachedContentTokenCount` (confirmed live against Vertex AI's `GenerateContentResponse.UsageMetadata` REST reference, 2026-09-09: "the number of tokens in the cached part of your input"). Before this change `git grep -i cache` in this file returned zero matches — not even the observability `google-adapter.ts`'s sibling API already had.

What's added — observability only, matching the mechanism (automatic, server-side, no request field): both `parseVertexAIResponse()` (non-streaming) and the SSE loop in `chatCompletionStream()` now read `usageMetadata.cachedContentTokenCount` and record it via `recordProviderPromptCacheUsage()`. Vertex only reports the hit count directly, so the miss count is derived as `promptTokenCount - cachedContentTokenCount`, the same derivation every other hit-only-reporting provider in this ADR uses. Unlike the standalone Gemini API adapter, Vertex AI's streaming path already parsed `usageMetadata` for token counts before this change, so streaming observability is NOT a gap here the way it is for `google-adapter.ts`.

### Now have it: Cohere — 2026-09-09

`api/src/providers/cohere/cohere-adapter.ts`. Cohere's Chat API v1 (`POST /v1/chat`, what this adapter used before) has no cache-related response field at all. Chat API v2 (`POST /v2/chat`) documents `usage.cached_tokens` — "the number of prompt tokens that hit the inference cache" (docs.cohere.com/v2/reference/chat, verified live 2026-09-09) — automatic, server-side, no request field to set. There was no way to close this gap without migrating off v1.

What's added: `chatCompletion()` and `chatCompletionStream()` now target `/v2/chat` — a single `messages` array (role `system`/`user`/`assistant`/`tool`) replaces v1's split `message` + `chat_history`, the assistant's text is read from `message.content[].text` instead of a flat `text` field, and `finish_reason` is mapped from v2's real documented enum instead of the previous unconditional `'stop'`. `recordCacheUsage()` reads `usage.cached_tokens` and records it via `recordProviderPromptCacheUsage()`, deriving the miss count from `usage.tokens.input_tokens` (preferred over `usage.billed_units.input_tokens`, which is already post-cache-discount billing and would understate real prompt size). Embeddings and the API-key health check are DELIBERATELY left on v1 — out of scope for this fix.

### Now have it: Groq, Azure OpenAI, Cerebras, SambaNova — 2026-09-09

All four are routed through the shared `OpenAICompatibleHubAdapter` and share one root cause: the hub's `recordHubCacheUsage()` (added for Moonshot on the not-yet-merged branch covering that provider) only recognized a FLAT `usage.cached_tokens` field. Each of these four documents the SAME nested `usage.prompt_tokens_details.cached_tokens` shape OpenAI itself uses instead — confirmed live 2026-09-09 against each vendor's own docs:

- **Groq** (`console.groq.com/docs/prompt-caching`): automatic for `openai/gpt-oss-20b`/`120b`/`safeguard-20b`, "no code changes required," cannot be disabled. No request-side field — observability only.
- **Azure OpenAI** (`learn.microsoft.com/.../ai-foundry/openai/how-to/prompt-caching`): automatic by default for GPT-4o+, PLUS the same `prompt_cache_key` request field OpenAI documents ("reuse the same key for requests that share long, common prompt prefixes"). `azure-openai-adapter.ts` extends the generic hub (not `openai-adapter.ts`), so it never inherited that field's wiring — closed via a new `getExtraChatPayloadFields()` override sending `prompt_cache_key: deriveSessionKey(request)`, the same derivation OpenAI/Mistral use.
- **Cerebras** (`inference-docs.cerebras.ai/capabilities/prompt-caching`): "automatically enabled for all models," PLUS an optional `prompt_cache_key` routing hint — same contract as Azure/OpenAI/Mistral. `cerebras-adapter.ts` already overrode `getExtraChatPayloadFields()` for `max_completion_tokens`; the override now also sends `prompt_cache_key` unconditionally.
- **SambaNova** (`sambanova.ai/blog/prompt-caching-on-sambacloud`): "Automatic Prefix Caching," live for MiniMax-M2.7, ≥4,096-token prefix threshold — automatic, no request field. Observability only.

Fix: `recordHubCacheUsage()` in `openai-compatible-hub-adapter.ts` now checks BOTH the flat `cached_tokens` field and the nested `prompt_tokens_details.cached_tokens` field, kept generic (not gated on `providerName`) for the same reason the original flat-field version was — this is a real, shared OpenAI-compatible-ecosystem convention, so any OTHER hub-routed provider that reports either shape gets the same honest observability for free.

### Now have it: Databricks (Claude-hosted endpoints) — 2026-09-09

`api/src/providers/databricks/databricks-adapter.ts`. Databricks documents `cache_control: { type: 'ephemeral' }` on a message content block — Anthropic's own mechanism — for Databricks-hosted Claude models (verified live 2026-09-09 against Databricks' community + REST API docs). Databricks' pay-per-token Foundation Model API names these endpoints `databricks-claude-<family>` (e.g. `databricks-claude-sonnet-4-5`), confirmed against Databricks' own supported-models listing.

What's added: `isDatabricksClaudeEndpoint()` name-pattern-detects a Claude-hosted endpoint (mirroring `aws-bedrock-adapter.ts`'s `isBedrockClaudeModel()` — same class of limitation: a custom-named endpoint that also wraps Claude is not detected). `applyDatabricksClaudeCacheControl()` marks the system message with a single `cache_control` breakpoint when its content is a plain string, mirroring ADR-025's own "single checkpoint" simplification for Bedrock. Deliberately scoped to the system message only — tool definitions and structured/array system content are OUT of scope, since the exact shape Databricks expects for `cache_control` on those, on this OpenAI-compatible-shaped endpoint specifically, could not be confirmed. No minimum-size gate, matching `anthropic-adapter.ts`'s own system-prompt breakpoint. Because Databricks routes through the shared hub, the same nested-format `recordHubCacheUsage()` fix above gives this provider cache-hit observability for free if Databricks reports the field in that shape.

### Have it (observability only) — deliberately incomplete: BytePlus / ModelArk — 2026-09-09

`api/src/providers/byteplus/byteplus-adapter.ts`. This file's own `ArkModelRecord` type already modeled `features.cache?: { prefix_cache?: boolean; session_cache?: boolean }` — the vendor's own per-model capability flag — but nothing in the file ever read it. ModelArk documents two real cache mechanisms, Session Cache and Prefix Cache (verified live 2026-09-09 against ModelArk/Volcengine Ark's Context Caching docs), both reporting `usage.prompt_tokens_details.cached_tokens` on ordinary `/chat/completions` responses.

What's added: `recordCacheUsage()` reads `usage.prompt_tokens_details.cached_tokens` from every chat response and records it via `recordProviderPromptCacheUsage()` — zero new request shape, so this is safe today.

**Deliberately NOT added**: activating either cache mode. Both require FIRST calling a separate context-creation endpoint to obtain a `context_id`, then threading that id through every subsequent request — genuine session/TTL state this stateless per-request adapter does not hold anywhere today, and the exact request contract for that flow (the create-call's endpoint path, and where the resulting id is threaded back into a `/chat/completions` call) could not be confirmed against ModelArk's docs in this pass (JS-rendered pages that did not yield their full content to automated fetching). Sending an unverified two-call flow risked a worse failure mode — extra failing requests — for a mechanism this pass could not prove out. `features.cache` is still read nowhere for capability-filtering either; wiring session/prefix-cache activation once the request contract is confirmed live is the explicit follow-up this section flags.

### Deliberately evaluated and excluded: OpenRouter

`api/src/providers/openrouter/openrouter-adapter.ts`. `extractPricing()` (`:396-422`) parses `input_cache_read` / `input_cache_write` pricing fields from OpenRouter's model metadata — this is cost **accounting** for whatever caching the upstream provider OpenRouter is routing to already did, not a caching **control** this adapter sends. OpenRouter fans a single request out across many different underlying providers and models, each with its own (or no) native caching mechanism; there is no single OpenRouter-level knob analogous to `cache_control` or `cachePoint` for this adapter to set. This is a genuine, verified architectural constraint, not an oversight — caching behavior here is provider-dependent and outside this repo's control.

### Confirmed automatic, zero code needed on the request side: Google Gemini — 2026-09-08

`api/src/providers/google/google-adapter.ts`. Gemini's "implicit caching" is enabled by default for Gemini 2.5+ models (ai.google.dev/gemini-api/docs/caching, verified live 2026-09-08) — no request-side field, no `cache_control`-style marker, nothing for this adapter to send. The original 2026-09-06 pass's assumption that Gemini *only* exposes the older, stateful "create a `CachedContent` object, then reference it by name" flow is now outdated: that explicit flow still exists (the SDK ships `GoogleAICacheManager` under `@google/generative-ai/server`, confirmed in `node_modules/@google/generative-ai/dist/server/server.d.ts`, and `GoogleGenerativeAI.getGenerativeModelFromCachedContent()` to reference one) and remains genuinely useful when a caller wants a *guaranteed* cache hit rather than implicit caching's best-effort — but it requires this adapter to own a cache-object lifecycle (create, track by content hash, renew or let expire, delete) that every other provider in this ADR handles with a single stateless per-request marker. **Deliberately not implemented here**: implicit caching already captures the automatic-savings case with zero infrastructure; building and operating a stateful cache-lifecycle subsystem for the narrower "guaranteed hit" case is a materially larger and riskier change than anything else in this ADR, and no request in this repo's traffic has yet demonstrated implicit caching's best-effort behavior is insufficient. Flagged here as a legitimate future follow-up, not a gap nobody noticed.

What's added instead — real, in-scope, low-risk observability: `convertResponse()` now reads `usageMetadata.cachedContentTokenCount` (confirmed field name in `@google/generative-ai`'s own `UsageMetadata` type, `dist/generative-ai.d.ts:1392`) and records it via `recordProviderPromptCacheUsage()`. Gemini only reports the hit count directly, so the miss count is derived as `promptTokenCount - cachedContentTokenCount`. **Streaming is NOT covered**: `convertStreamChunk()` doesn't surface `usageMetadata` at all today for ANY field, not just this one — a pre-existing gap this change doesn't widen or fix, since fixing it is unrelated to prompt caching specifically.

Per-model minimum thresholds for implicit caching to engage (same doc, informational — there is no client-side gate to apply since implicit caching is 100% server-side): 2,048 tokens for Gemini 2.5 Flash/Pro; 4,096 tokens for the 3.x Flash family and 3.1 Pro Preview.

### Confirmed automatic, zero code needed on the request side: DeepSeek — 2026-09-08

`api/src/providers/deepseek/deepseek-adapter.ts`. DeepSeek's context caching on disk is "enabled by default for all users... without needing to modify their code" (api-docs.deepseek.com/guides/kv_cache, verified live 2026-09-08) — confirms the original assumption exactly; there was nothing to add on the request-building side.

What's added — real, in-scope observability, plus a genuine bug fix uncovered while investigating it: DeepSeek's response `usage` object reports BOTH `prompt_cache_hit_tokens` and `prompt_cache_miss_tokens` directly (no derivation needed, unlike every hit-only provider above). The non-streaming `chatCompletion()` path already returned the raw parsed JSON verbatim (so these fields technically reached callers via untyped duck-typing already) — `recordDeepSeekCacheUsage()` now makes that observability explicit and queryable. The **streaming** path (`convertStreamChunk()`) had a real, separate bug: it explicitly reconstructed a narrowed usage object containing only `prompt_tokens`/`completion_tokens`/`total_tokens`, silently discarding both cache fields even when DeepSeek's own SSE chunk carried them — an asymmetry between the two request paths that existed before this change and is now fixed by recording the raw usage object's cache fields before that narrowing happens.

### Confirmed automatic, zero code needed on the request side: Moonshot / Kimi — 2026-09-08

`api/src/providers/moonshot/moonshot-adapter.ts` (thin subclass of `openai-compatible-hub-adapter.ts` — see that file's `MoonshotAdapter`). This is the one provider in this ADR where the real 2026-09-08 finding actively **contradicts** the original assumption: Moonshot's Kimi API used to document (and some third-party write-ups still describe) a separate manual "create a cache, get a `cache_id`, reference it" flow. As of today, Moonshot's own current docs describe fully automatic caching instead: "Context Caching is automatically enabled for all model requests... no manual cache creation or management required" (platform.kimi.ai/docs/guide/use-context-caching-feature-of-kimi-api.md, verified live 2026-09-08). Caching activates once a request's prompt exceeds 256 tokens; there is no manual API surface left to call, and nothing for this adapter to send.

What's added: since Moonshot is routed through the shared `OpenAICompatibleHubAdapter` (not a Moonshot-specific request path), `recordHubCacheUsage()` is added to the SHARED hub adapter rather than gated on `providerName === 'moonshot'` — Moonshot's response `usage.cached_tokens` (flat field, confirmed at platform.kimi.ai/docs/api/chat, verified live 2026-09-08) is a real OpenAI-compatible-ecosystem convention, so any other hub-routed provider that happens to report the same field gets the same honest observability for free, correctly labeled by its own `providerName`. Wired into both `chatCompletion()` code paths (explicit model, and the auto-fallback candidate loop) and `convertStreamChunk()`.

## Consequences

### Positive
- The Anthropic/Bedrock inconsistency that prompted this audit is closed for the Claude family: the same model now gets caching through either path.
- One document now answers "does provider X cache prompts here" for every provider, with file:line citations, instead of that knowledge living only in whichever engineer last touched a given adapter.
- `buildConverseInput()` removes a duplicated-construction hazard in the Bedrock adapter that made the streaming and non-streaming paths capable of silently diverging.
- (2026-09-08) Mistral and xAI gained a real request-side caching control this repo wasn't using (`prompt_cache_key` / `x-grok-conv-id`), using the exact same `deriveSessionKey()` derivation OpenAI already relied on — so all three providers' cache-lineage keying can never drift from each other.
- (2026-09-08) `ci_provider_prompt_cache_tokens_total` (`api/src/observability/ci-metrics.ts`) closes the cache-hit-observability gap (see Negative, below) for every provider whose response `usage` already reports a hit-token count — DeepSeek, Moonshot, Google Gemini, xAI, and Mistral — without touching the shared `Usage` type, addressing Alternative C's concern non-invasively.
- (2026-09-08) A real, separate bug was found and fixed while investigating DeepSeek: `deepseek-adapter.ts`'s streaming path silently discarded `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens` even when DeepSeek's own SSE chunk carried them, while the non-streaming path passed them through untouched — an asymmetry nobody had noticed because nothing consumed either field either way until now.
- (2026-09-09) Vertex AI, Cohere, Azure OpenAI, Cerebras, and Databricks each gained real cache observability or a real request-side control this repo wasn't using; Groq, SambaNova, and BytePlus gained observability for a mechanism that was already running silently. `ci_provider_prompt_cache_tokens_total` now covers nine more providers without any `Usage`/`ChatResponse` shape change.
- (2026-09-09) The hub's `recordHubCacheUsage()` recognizing both the flat and nested `cached_tokens` shapes means any FUTURE hub-routed provider that documents either convention gets correct observability automatically, with no per-provider code required.

### Negative
- The Bedrock minimum-token table (`CLAUDE_CACHE_MIN_TOKENS`) is a static snapshot of AWS's documentation as of 2026-09-06. AWS revises per-model minimums as it ships new Claude versions; this table will drift unless it's revisited alongside future Bedrock model onboarding. The conservative fallback (4,096 tokens) bounds the damage of drift to "caches less than it optimally could," never to a broken request.
- `Usage` (`api/src/types/index.ts:759-763`, still a fixed `{ prompt_tokens, completion_tokens, total_tokens }` shape) still carries no cache fields, and Anthropic-direct/Bedrock/OpenAI still don't surface their own cache-read/cache-write counts anywhere (Bedrock's `TokenUsage.cacheReadInputTokens`/`cacheWriteInputTokens` and Anthropic's own `cache_creation_input_tokens`/`cache_read_input_tokens` are both real, unread data). `ci_provider_prompt_cache_tokens_total` closes this gap only for the providers evaluated across this ADR's two updates (fourteen total), each of which already had a hit-token field in its raw `usage` response the adapter could read without any shape change; extending the same treatment to Anthropic/Bedrock/OpenAI remains a real, valuable, explicitly NOT-done-here follow-up.
- (2026-09-06, resolved 2026-09-08/09) The five "not yet evaluated" providers from the original version of this ADR (Google Gemini, DeepSeek, Moonshot/Kimi, Mistral, xAI), plus the nine more found in the 2026-09-09 sweep, have now all been evaluated — see each provider's own section above. Google Gemini's *explicit* `CachedContent` caching remains a known, real, deliberately-unimplemented mechanism (stateful cache-lifecycle management judged not worth the operational cost over implicit caching's zero-infrastructure automatic coverage) — that specific piece is the one genuine remaining gap this ADR still flags rather than closes.
- BytePlus/ModelArk's Session Cache and Prefix Cache remain un-activated (observability only) — see that provider's own section above for why the request-side activation flow could not be confirmed and implemented safely in this pass.
- Databricks' `cache_control` is scoped to the system message only; tool definitions and array-shaped system content are a known, flagged gap, not a silent omission.

## Alternatives considered

**A. Mirror Anthropic-direct's two-breakpoint (tools + system, independently) placement in Bedrock.** Rejected in favor of AWS's own documented single-breakpoint "simplified cache management" recommendation for Anthropic models on Bedrock — two independent checkpoints add complexity (and consume more of the 4-checkpoint-per-request budget) for no benefit once checkpoints are known to be evaluated cumulatively in a fixed section order.

**B. Skip the minimum-token gate entirely and always emit `cachePoint`.** Rejected: while not an API error, it would misrepresent what the code is doing — emitting a marker known in advance to never cache anything. Gating keeps the emitted request honest about its own effect.

**C. Extend `Usage` to carry cache-read/cache-write token counts as part of this change.** Rejected as scope creep: this is a pre-existing gap shared by every provider (see Consequences), not something introduced or worsened by this fix. Flagged here for a future, dedicated pass rather than folded in silently. **(2026-09-08 update: still rejected, for the same reason — see the new `ci_provider_prompt_cache_tokens_total` metric instead, which delivers the same observability value as a non-breaking side channel rather than a `Usage`/`ChatResponse` shape change. 2026-09-09 update: still rejected — every provider closed in that update's sweep also funnels into the same metric.)**

**D. (2026-09-08) Implement Google Gemini's explicit `CachedContent` create-then-reference flow.** Rejected for now: it requires this adapter to own a stateful cache-object lifecycle (create, track by content-hash, renew before expiry or let it lapse, delete) that every other mechanism in this ADR — Anthropic's `cache_control`, Bedrock's `cachePoint`, OpenAI/Mistral's `prompt_cache_key`, xAI's `x-grok-conv-id` — avoids entirely by being a stateless per-request marker. Gemini's implicit caching (automatic, default-on for 2.5+ models, zero code) already captures the automatic-savings case; explicit caching's only advantage is a *guaranteed* hit instead of implicit's best-effort, a narrower benefit that hasn't been shown to matter for this repo's actual traffic. Revisit if implicit caching's hit rate proves insufficient in practice.

**E. (2026-09-08) Gate Mistral's `prompt_cache_key` on a minimum-prompt-token estimate, mirroring Anthropic's/Bedrock's minimum-cacheable-size gates.** Rejected: unlike `cache_control`/`cachePoint` (markers that change the request's shape and are worth omitting when known-useless), `prompt_cache_key` is unconditionally safe to send regardless of prompt size — it is just a stable string, unconditionally sent by OpenAI's identical mechanism too. Mistral's documented 64-token cache-block minimum is the vendor's own internal eligibility rule, evaluated the same way regardless of what the client sends; there is no request-shape branch for this adapter to gate.

**F. (2026-09-09) Implement BytePlus/ModelArk's Session/Prefix Cache request-side activation in this same pass.** Rejected for now: both require a stateful create-then-reference flow (obtain a `context_id`, thread it through subsequent requests) whose exact request contract could not be confirmed against ModelArk's docs in this pass. Shipping an unverified two-call flow risks extra failing requests for zero proven benefit — worse than shipping observability alone. Revisit once the request contract is confirmed live.

**G. (2026-09-09) Extend Databricks' `cache_control` to tool definitions and array-shaped system content, matching Anthropic-direct's full coverage.** Rejected for now, same reasoning as Bedrock's own single-checkpoint simplification (Alternative A): the exact shape Databricks' OpenAI-compatible-shaped endpoint expects for `cache_control` outside a plain-string system message is unverified, and the system message alone is the highest-value, lowest-risk target.
