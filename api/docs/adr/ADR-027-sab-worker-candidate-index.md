# ADR-027: SharedArrayBuffer + `worker_threads` Candidate Index (`SELECTION_USE_SAB_CANDIDATE_INDEX`)

**Status**: Accepted (implementation shipped, flag default OFF pending real production load-test evidence)
**Date**: 2026-09-09
**Context**: ADR-026 (`SELECTION_USE_FULL_CACHE_INDEX` rollout readiness) found that flag's in-process Map-scan candidate-retrieval path is a real, measured production risk: it runs synchronously on the MAIN thread and blocks the event loop for every other in-flight request on the same process for the full duration of the scan (median 14.6s / max 32.5s at N=500 concurrent, worse than the SQL path it was meant to replace). ADR-026's Precondition 1 was: "move the O(catalog) scan off the main thread" — this ADR is that work.
**Related**: ADR-026 (full-cache-index-rollout-readiness, precondition this closes), `investigation/sab-worker-feasibility/REPORT.md` (PR #531, the feasibility investigation this implements), `api/src/core/selection/dynamic-model-selector.ts` (`getFullCacheFairCandidateModels`, `getSabCandidateModels`), `api/src/core/selection/sab-candidate-index/` (this implementation).

## Decision

Ship a production `worker_threads`-owned, `SharedArrayBuffer`-backed double-buffer candidate index as a THIRD candidate-retrieval path, gated behind its own new flag `SELECTION_USE_SAB_CANDIDATE_INDEX` (default OFF), taking priority over `SELECTION_USE_FULL_CACHE_INDEX` when both are enabled, falling open to that path (and ultimately to the SQL path) whenever the SAB index isn't ready yet.

### Why a new flag, not reusing `SELECTION_USE_FULL_CACHE_INDEX`

The two paths solve the SAME problem (the SQL path's 400/bucket ceiling) but with architecturally unrelated mechanisms — an in-process `Map` scan vs. a separate OS thread + shared memory. Reusing the existing flag would mean "the flag's meaning silently changes to a completely different implementation", which:
1. Makes ADR-026's own measured numbers (which are specifically about the Map-scan implementation) misleading if left attached to a flag whose behavior later changed underneath them.
2. Removes the ability to roll back to the (slower but well-understood) Map-scan path independently of turning this new path off, if the SAB path's own risks (crash/respawn behavior, memory cost, worker-owned-DB-connection pattern) surface a problem in production the Map path wouldn't have.
3. Matches this repo's own convention of flag-per-mechanism (see `SELECTION_PREFILTER_CALLABLE`, `SELECTION_POPULARITY_SEED`, `SELECTION_USE_FULL_CACHE_INDEX` itself) rather than flag-per-goal.

## Design summary

- **A long-lived `worker_threads.Worker`** (`sab-candidate-index/worker.ts`) owns building/rebuilding a double-buffered `SharedArrayBuffer` index. It fetches catalog rows via its OWN, independent connections — a small dedicated `PrismaClient`/`pg.Pool` (see "Prisma + worker_threads" below) for the Postgres fallback, and the existing `getRedisClient()` for the Redis-first fetch (same `CATALOG_REDIS_KEY` fleet-wide snapshot `model-catalog-service.ts` already publishes) — never receiving catalog rows via `postMessage` from the main thread (see "The postMessage constraint" below).
- **The main thread's manager** (`sab-candidate-index/manager.ts`) allocates the three `SharedArrayBuffer`s (two generations + a small Atomics control block) ONCE and hands the SAME buffers to every worker instance it ever spawns via `workerData`. A worker crash is caught (`'error'`/`'exit'` events — confirmed non-fatal to the main process, see the feasibility investigation's Finding 2) and triggers an automatic respawn with the same buffers, so reads keep serving the last-good generation throughout the crash/respawn window with zero data loss (a deliberate improvement over the feasibility prototype, which had the worker itself own buffer allocation — see `manager.ts`'s own module doc for the full reasoning).
- **The read path** (`sab-candidate-index/reader.ts`) is synchronous, zero-I/O, and reads pre-sorted/pre-grouped typed arrays directly — O(candidates returned), never O(catalog size). It is a byte-for-byte faithful port of `getFullCacheFairCandidateModels`'s semantics, verified by `__tests__/encode-reader-correctness.test.ts` against the REAL, shipped function across the same 8-case filter-combination matrix the original feasibility investigation used.
- **Scope, explicitly**: this closes the gap for ONE process/replica. Cross-replica coordination is NOT addressed — `SharedArrayBuffer` is confirmed strictly intra-process (feasibility investigation Finding 1), so each `ci_api` replica runs its own independent worker + `SharedArrayBuffer` pair. Postgres remains the fleet-wide source of truth; the existing Redis fleet-wide snapshot (`CATALOG_REDIS_KEY`) remains the cross-replica synchronization point each replica's own worker reads from first.

## Deviations from the feasibility prototype (and why)

1. **The manager, not the worker, owns `SharedArrayBuffer` allocation.** See above — this makes crash+respawn lossless and simple, at the cost of the manager needing to know the buffer layout ahead of spawning the first worker (a small, acceptable coupling — both sides already share `schema.ts`/`capacity.ts`).
2. **Full `metadata` fidelity, not just the two flags the original investigation cared about.** The prototype's `encode.mjs` only preserved `hubInventoryClass`/`serverless_callable` (folded into `bucketFlag`) — sufficient for its own correctness comparison, but NOT sufficient for production: `findModelsByRequirements`' `requiredTools`/`requiredEndpoint` filters, `popularityPriorFromMetadata`, and several scoring reads (`metadata.executionProvider`, `metadata.version`) all run downstream of candidate retrieval, unconditionally, against whatever `metadata` the candidate carries. Silently returning `metadata: undefined` from this path would have silently broken every one of those for every SAB-path candidate. Fixed by encoding the full `JSON.stringify(model.metadata)` per row into its own blob (`METADATA_BLOB_BYTES`, default 64MB) — a real, additional memory cost beyond what the original investigation measured (see "Memory cost" below).
3. **Redis-first, not Postgres-only, worker fetch.** The prototype's `worker.mjs` never fetched anything (it received a fixture array as a proof-of-concept). A naive "worker always queries Postgres directly on its own timer" design would reintroduce the exact per-replica-multiplication problem `model-catalog-service.ts`'s `catalog-cache-refresh` BullMQ election mechanism already exists to prevent (N replicas each independently hitting Postgres for the same full-catalog query). The worker instead reads the SAME fleet-wide Redis snapshot every other consumer already reads, falling back to its own direct Postgres query only when that snapshot is empty/unreachable — matching `resolveColdCatalog`'s own fail-open chain.
4. **Capability-bitmask overflow degrades gracefully instead of failing the rebuild.** SUPERSEDED on 2026-09-11 (see "Canary 2" below): this deviation was wrong end to end. The original reasoning was that the prototype threw on `>32 distinct capabilities` and production could not afford to fail an entire rebuild over it, so the encoder truncated to the first 32 sorted names and relied on the reader's fail-open rule. What that reasoning missed is that the reader also DECODES capabilities from the same truncated list, so every dropped capability vanished from the returned `Model`, and `findModelsByRequirements`' fail-closed post-hydration filter then emptied the pool for any request requiring one of them. The mask is now 4 x 32 = 128 bits (`CAPABILITY_MASK_WORDS`, `capability-mask.ts`), and exceeding it is a hard `SabEncodeCapacityError` like every other capacity bound: the last-good generation keeps serving and `ci_sab_candidate_index_build_failures_total{reason="capacity"}` increments.

## Prisma Client + `worker_threads` (investigated per this PR's explicit requirement)

A `PrismaClient` instance cannot be shared as a live object across a `worker_threads` boundary — like any object wrapping native bindings/sockets, it is not structured-clone-able. The correct pattern (used here): each worker thread constructs its OWN independent `PrismaClient`, which falls out naturally from `worker_threads` giving every `Worker` a fresh module registry (importing a module inside a worker file does not reuse whatever the main thread already instantiated from that module — it re-runs the module's top-level code in the worker's own realm).

The easy-to-miss risk this surfaces: naively importing the app's existing shared `@/database/client` module from inside the worker would silently construct a SECOND full-size connection pool (`config.database.poolMax`, 30 in production) per replica, compounding the exact connection-budget concern ADR-026 already flags (`DB_POOL_MAX`/replica × 2 replicas + 1 worker ≈ 300 vs Postgres's `max_connections=200`). `worker.ts` therefore does NOT import `@/database/client` — it constructs its own minimal `PrismaClient` with a small, dedicated pool (`WORKER_DB_POOL_MAX`, default 2), justified because this is a low-QPS fallback path (Redis is checked first) that never runs more than one query at a time.

To share `CATALOG_HOT_PATH_SELECT`/`mapPrismaModel` (the exact Prisma select allowlist + row mapper `model-catalog-service.ts`'s own cold path uses) without pulling in that heavy shared-pool module, these were extracted into a new, dependency-light module (`@/services/catalog-hot-path.ts`) that only imports Prisma TYPES, not the client. `model-catalog-service.ts` now imports and re-exports them for backward compatibility.

## A real bug this PR's own testing found: `@/` path aliases do not resolve inside a `worker_threads` Worker

Not part of the original investigation (its scripts were plain `.mjs` with no path-alias system to worry about) — found while writing this PR's own real DB-backed benchmark test, which is the first thing in this codebase to actually spawn a worker importing files that use this project's `@/` -> `src/` alias.

**Confirmed empirically, twice:** neither a bare `new Worker(path)` nor `new Worker(path, { execArgv: ['--import', 'tsx'] })` resolves a `@/`-aliased import inside the spawned worker — both fail with `ERR_MODULE_NOT_FOUND`, under BOTH plain `tsx` (`tsx src/index.ts`-style execution) and under `vitest`. `tsx` resolves `@/` correctly for its OWN entry file (confirmed working), but that resolution does not propagate into a `worker_threads` Worker it spawns, even when that worker's own `execArgv` re-imports `tsx` itself. This would have broken `worker.ts` in EVERY execution mode except the fully compiled production build (`tsc-alias` rewrites `@/` to real relative paths at build time, so `dist/**/worker.js` never hits this) — meaning local dev (`pnpm dev`) would have been silently broken had this not been caught before merge.

**Fix**: `sab-candidate-index/dev-alias-resolver-hook.mjs` + `dev-alias-resolver-preload.mjs` — a small, hand-written Node ESM `resolve` customization hook (`module.register()`, Node 20.6+). `manager.ts`'s `resolveWorkerExecArgv()` passes this hook to the worker via `execArgv: ['--import', <preload as a file:// URL>]` — but ONLY in the non-compiled (dev/test) case; the compiled build gets `[]` (no-op).

**Correction (2026-09-10, see "A second real bug" below): the claim that originally stood here — that the compiled build's `worker.js` has "no aliased/extension-less references left to rewrite" because "`tsc-alias` already resolved everything to explicit relative paths at build time" — was WRONG, and was never actually verified against a real `pnpm build` output before this PR merged. It was true for every `@/`-aliased import in this file EXCEPT ONE: `@/generated/prisma/index.js`. See below for why that one specifically survives `tsc-alias` unrewritten, and why `execArgv: []` being correct for the dev-alias-hook problem does not mean the compiled build was actually alias-free.

**Why not `module-alias` or `tsconfig-paths`** (both considered, `module-alias` is already an unused project dependency): both are CommonJS `Module._resolveFilename` patches. `tsx` loads `.ts` files with ESM syntax as real ES modules (confirmed by the exact error shape — Node's ESM resolver, not its CommonJS one — and by a `MODULE_TYPELESS_PACKAGE_JSON` reparse-as-ESM warning), so a CommonJS-only alias patch would not intercept this resolution at all. The fix had to be an ESM `resolve` hook specifically.

**This took three iterations to get fully right — each one found by actually running the real worker, not by inspection:**
1. `@/`-prefixed specifiers (e.g. `@/utils/logger`) — fixed by rewriting `@/` to the real `src/` path with an extension-candidate search (`.ts`/`.tsx`/`.js`).
2. Plain extension-less RELATIVE specifiers (e.g. `worker.ts`'s own `import { computeLayout } from './schema'`) — real Node ESM resolution (unlike CommonJS or `tsx`'s own resolution) requires an explicit extension and does not guess `.ts` for a relative import either. Fixed by applying the same extension-candidate search to `./`/`../` specifiers, resolved against `context.parentURL`.
3. Directory imports (e.g. `@/config`, which resolves to the real DIRECTORY `src/config/`, not a file) — a bare `fs.existsSync` check on the candidate path incorrectly accepted the directory itself as a match; real Node ESM does not auto-resolve a directory to its `index.ts` the way CommonJS/`tsx` do. Fixed by checking `fs.statSync(...).isFile()` before accepting any candidate, with an explicit `index.ts`/`index.js` fallback.

Verified end to end by spawning the REAL `worker.ts` directly (not a stand-in) and observing a genuine `{"type":"ready"}` message, then a genuine `rebuild-failed` message carrying a real Prisma connection error (not a resolution error) when pointed at a deliberately-fake `DATABASE_URL` — proof the entire transitive import graph resolves correctly before ever reaching real I/O. Confirmed working under both plain `tsx` and `vitest` before being wired into `manager.ts`, and the full real DB-backed benchmark suite (below) passed end to end afterward.

**Gap in this verification, found by the production canary (see next section): every one of these checks ran against `tsx`/`vitest`, i.e. the raw `.ts` source. None of them ran against the actual `pnpm build` output (`dist/`). That gap is exactly what let the second bug below reach production.**

## A second real bug: the compiled build was NOT actually alias-free — `src/generated/prisma` is excluded from `tsc`'s own compilation

**Found by**: the `SELECTION_USE_SAB_CANDIDATE_INDEX` production canary, rolled out after this PR merged, which crash-looped and was reverted. Every worker respawn attempt in the production logs failed identically:

```
Error: Cannot find module '@/generated/prisma/index.js'
Require stack:
- /app/dist/core/selection/sab-candidate-index/worker.js
```

**Root cause**: `worker.ts` imports `PrismaClient` the same way every other file in this codebase does — `import { PrismaClient } from '@/generated/prisma/index.js'` — an `@/`-aliased specifier, exactly like the `@/utils/logger`/`@/cache/redis-client`/`@/services/catalog-hot-path` imports a few lines below it in the same file. `pnpm build` (`tsc && tsc-alias`) rewrites those other three to real relative paths in the compiled output (confirmed: `require("../../../utils/logger")`, etc.) — but it does NOT rewrite the Prisma one; the compiled `dist/core/selection/sab-candidate-index/worker.js` was shipping the literal, unrewritten string `require("@/generated/prisma/index.js")`.

Why this one specifier and no other: `api/tsconfig.json`'s `exclude` list contains `src/generated/**/*` (Prisma's `schema.prisma` generator target, `output = "../src/generated/prisma"`) — it is excluded from `tsc`'s compilation set on purpose, so `tsc` never type-checks or emits it as part of the normal build (`api/Dockerfile`'s build stage copies the already-generated JS out of `src/generated/prisma` into `dist/generated/prisma` as its own separate, explicit step, specifically because `tsc` will not do it). `tsc-alias` rewrites an `@/`-aliased import by computing the compiled-output-relative path of whatever `tsc` actually emitted for that source file; since `src/generated/prisma/index.js` is never part of `tsc`'s own emitted-file set, `tsc-alias` has nothing to map the alias onto and leaves the specifier untouched. Every OTHER `@/`-aliased import in this codebase points at a file `tsc` does compile (everything under `src/` outside `src/generated/`, `src/tests/`, `src/client/`), which is why this is the only import in this file — and the only place in the whole codebase — where this gap is visible.

Why the main thread never showed this symptom: `app.cjs` (the real production entrypoint, `CMD ["node", "dist/app.cjs"]` in `api/Dockerfile`) calls `require('module-alias/register')` and `addAliases({ '@': distDir, ... })` BEFORE requiring the app (`require('./index.js')`), which patches Node's CommonJS `Module._resolveFilename` fleet-wide for that process — so `require('@/generated/prisma/index.js')` from e.g. `dist/database/client.js` resolves via that patch to `dist/generated/prisma/index.js`, which does exist (copied there by the Dockerfile step above). `manager.ts`'s `resolveWorkerPath()` spawns this worker with `new Worker(path.join(__dirname, 'worker.js'))` — a direct `worker_threads` spawn of the compiled file, which never executes `app.cjs` and therefore never installs the `module-alias` patch. The literal `@/generated/prisma/index.js` string is not a valid relative or absolute path and is not a builtin module, so Node's unpatched CommonJS resolver in the worker thread fails immediately with `MODULE_NOT_FOUND` — before the worker can emit its `{"type":"ready"}` message, so `manager.ts`'s `worker.on('error', ...)` → `scheduleRespawn()` path (correctly, by design) keeps respawning a worker that can never succeed, which is the crash-loop the canary hit.

**Fix**: changed `worker.ts`'s import of `PrismaClient` from the `@/`-aliased specifier to a literal relative import — `'../../../generated/prisma/index.js'` — the exact path `tsc-alias` would have produced had it been able to process this specifier, confirmed against a real `pnpm build` (see Verification below). This is a targeted exception for this one import, not a reversion of this codebase's alias convention: every other import in `worker.ts` keeps using `@/`, because every other one resolves correctly in the compiled build.

**Verification against the real compiled build (not `tsx`/`vitest`)**: `pnpm build` run for real, `dist/` inspected directly — confirmed `dist/core/selection/sab-candidate-index/worker.js` now contains `require("../../../generated/prisma/index.js")` (previously the literal, unrewritten `require("@/generated/prisma/index.js")`), and confirmed `dist/generated/prisma/index.js` exists at that path once the Prisma-copy build step runs. Then the REAL compiled `worker.js` (not `worker.ts`, not a stand-in) was spawned directly as a `worker_threads.Worker` — the same way `manager.ts`'s `resolveWorkerPath()` does in production, with no `app.cjs`/`module-alias` bootstrap involved — and observed to reach a genuine `{"type":"ready"}` message with zero module-resolution errors. A negative-control run (temporarily reverting just the compiled `worker.js`'s require line back to the literal alias, everything else unchanged) reproduced the exact `Cannot find module '@/generated/prisma/index.js'` error from the production canary logs, confirming this harness actually exercises the failure mode the canary hit rather than a different one. This is the compiled-build check the original verification (previous section) was missing.

## The `postMessage` constraint

The single most important, least-obvious constraint this design depends on (feasibility investigation Finding 6, `postmessage-cost.mjs`): if the worker ever receives catalog rows via `worker.postMessage(rows)` from the main thread, the synchronous structured-clone serialization of that call ALONE blocks the main thread for 1.2–1.7 SECONDS on the real 111,666-row catalog — comparable to or worse than the very problem this design exists to solve. `manager.ts` only ever sends the worker a zero-payload `{ type: 'rebuild' }` signal; the worker fetches and encodes entirely on its own thread and reports back only small metadata (provider table, capability names, row counts — never per-model data).

## Memory cost (real, measured)

**455.01 MiB virtual per `ci_api` replica** (227.50 MiB x 2 generations + a 64-byte control block), measured directly from `computeLayout()`'s real byte offsets (`__tests__/memory-footprint.test.ts`), not estimated. Breakdown per generation: 195.31 MiB metadata blob (`MAX_MODELS` 200,000 x `METADATA_BYTES_PER_MODEL` 1,024), 12 MiB id blob, 3.05 MiB capability mask (4 words x 200,000 rows), ~17 MiB of fixed per-row numeric fields and ranking arrays.

History: the feasibility prototype measured 56.75 MB (no metadata blob); the first production schema measured 187.80 MiB (93.90 MiB x 2, with a flat 64 MiB metadata blob and a single-word capability mask). That 64 MiB was never multiplied against the real catalog and overflowed on the first real build (see "Canary 2"); the current default is derived from `MAX_MODELS` so the two constants cannot drift apart again, and covers the 2026-09-11 catalog (112,140 rows x ~976 bytes = ~109 MB) with 1.87x headroom.

This figure is VIRTUAL. The kernel backs `SharedArrayBuffer` pages lazily, so resident memory grows with bytes actually written: roughly 2 x (metadata used + id blob used + fixed fields touched), about 2 x 145 MB at today's catalog. The real RSS delta per replica with the flag on must still be confirmed by the next canary (Precondition 1).

This is the PERMANENT allocation only. It does not cover the worker's own TRANSIENT heap cost of actually building a generation — see the next section.

## Worker transient heap cost & `resourceLimits` (real, measured against real production data)

The SharedArrayBuffer figure above is the steady-state resident cost of the encoded index itself. Every rebuild cycle also has to fetch the catalog into plain JS objects BEFORE `encodeGeneration()` can write it into that buffer (`fetchCatalogModels()` in `worker.ts`) — a separate, transient allocation inside the worker's own V8 isolate that disappears once the rebuild returns, but is real while it lasts and, unbounded, is a real risk on its own.

Measured directly (2026-09-10, `node --expose-gc`, run against the running production `ci_api` container's own already-established Prisma connection — a single read-only `SELECT`, no writes, no schema changes, no data left the trusted production environment) rather than estimated against a synthetic fixture:

- Real row count at measurement time: **96,118** non-disabled rows (today's real number — smaller than the 111,666-row shape this PR's own test fixtures use, which is itself a real, still-growing figure, not a fixed constant; `capacity.ts`'s `MAX_MODELS` design ceiling is 200,000, ~2.1x today's count).
- Real column sizes: `metadata` averages 982 bytes/row (max observed 6,962 bytes), `capabilities` averages 33 bytes/row, `performance` averages 155 bytes/row.
- Postgres-fallback fetch path (`prisma.model.findMany` + `.map(mapPrismaModel)`): heapUsed grew from a ~30MB pre-fetch baseline to ~232MB for the raw Prisma records, peaking at **~280MB** once the mapped `Model[]` output is also transiently co-resident (the real peak, not a proxy — both arrays are alive simultaneously inside the `.map()` call).
- Redis-snapshot fetch path (the normal, cheaper-in-theory path): a `JSON.stringify` of the equivalent mapped payload produced 120.38MB of source text; the parse side of that path (source string + the object graph it decodes into, transiently co-resident) is the more expensive of the two paths and pushed measured heapUsed to **~521MB** at today's row count.

`resourceLimits: { maxOldGenerationSizeMb: 1536, maxYoungGenerationSizeMb: 256 }` (env-overridable via `SAB_CANDIDATE_WORKER_MAX_OLD_GEN_MB`/`SAB_CANDIDATE_WORKER_MAX_YOUNG_GEN_MB`, `manager.ts`'s `resolveWorkerResourceLimits()`) is the measured ~521MB Redis-path peak scaled linearly by the same ~2.1x growth ceiling (`MAX_MODELS`), rounded up for average-metadata-size growth (today's average is 982 bytes but the max already observed is 6,962 bytes — a fatter average is a realistic future) and V8 fragmentation.

Why this matters even though it defaults OFF: without an explicit `resourceLimits`, a `new Worker()` does NOT inherit a scaled-down slice of the main thread's `--max-old-space-size=3072` heap budget — it gets its own independent V8 isolate whose default ceiling is computed from total system memory, effectively unbounded relative to this container's actual 4G RSS hard limit (`docker/docker-compose.production.yml`). A runaway/looping rebuild in the worker could grow its heap independently of, and in addition to, the main thread's own usage — a real path to an uncontrolled whole-process OOM-kill, not just a worker failure. With the limit in place, a worker that somehow exceeds it is terminated and surfaces through the EXISTING `worker.on('error', ...)` → `scheduleRespawn()` path (`manager.ts`) — no new crash-handling code needed, reads keep serving the last-good generation throughout, exactly like any other worker crash this design already handles.

## Why the default stays OFF

Per this session's explicit instruction: do not promote to default-on without real, measured evidence that it resolves ADR-026's problem without introducing a new one. This PR ships the mechanism and the evidence (see Verification) but leaves the flag OFF, matching ADR-026's own precedent (ship correct + tested, default off, revisit once there is real production signal). Turning it on fleet-wide is a follow-up decision for whoever reviews the evidence below, not something this PR self-authorizes.

## Preconditions before this can safely become the default

1. **A canary/percentage rollout, or at minimum one real production replica running it under real traffic for a meaningful window**, observing: worker respawn frequency (should be ~zero in steady state), `lastSource` distribution (should be overwhelmingly `redis`, not `postgres` — a persistent `postgres` fallback rate would indicate the Redis fleet-wide snapshot mechanism itself is unhealthy, a pre-existing concern this PR does not fix), and real RSS/heap delta per replica against the measured figure below.
2. **`ADR-026`'s own Precondition 4** (turn on `ADMISSION_CONTROL_ENFORCE` with real thresholds) is equally applicable here — this PR removes the MAIN failure mode ADR-026 found, but does not add new backpressure of its own, and shouldn't be treated as a substitute for it.
3. **Watch the capability-mask headroom** (`MAX_CAPABILITIES = 128`, `CAPABILITY_MASK_WORDS = 4`) against the real, live distinct-capability count: 64 on 2026-09-11 (not the "~17" this precondition originally claimed). The count is exported per successful build as `ci_sab_candidate_index_distinct_capabilities`; an alert at, say, 112 (7/8 of the width) gives time to widen the mask before a rebuild starts failing with `reason="capacity"`. Corrected 2026-09-11: the `capabilitiesTruncated` field this precondition used to reference never existed in `getSabCandidateIndexStatus()` and the concept is gone (truncation is now a hard failure).
4. **A NEW canary/percentage rollout**, distinct from the one that already ran and was reverted for the compiled-build `@/generated/prisma` crash-loop documented above — the first canary's respawn-frequency/`lastSource` evidence is not valid signal for Precondition 1 above, since every worker in that canary was crash-looping on module resolution before it ever reached a real rebuild. This ADR's fix (relative import + verified against a real `pnpm build`, not just `tsx`/`vitest`) removes the crash-loop cause, but a fresh canary run is still required to gather the actual respawn-frequency/`lastSource`/RSS evidence Precondition 1 asks for — this PR does not, and should not, self-authorize re-enabling the flag.

## Canary 2 (2026-09-11): the index never became ready, and why

### What happened

A second canary ran `SELECTION_USE_SAB_CANDIDATE_INDEX=true` on one `ci_api` replica (image `70bc97c2`, which contains PR #562's Prisma-alias fix). The compiled-build crash loop from the first canary was gone: the `worker_threads` worker started, reached `ready`, and the manager requested the initial build. That build then failed, on every rebuild tick, and the index never served a single request. Selection fell through to the SQL bucket-fair path for the whole window (the replica did not have `SELECTION_USE_FULL_CACHE_INDEX` on). The flag was reverted to `false`.

Two independent bugs surfaced in the worker's log, in this order:

1. `sab-candidate-index-encode`: `distinctCapabilities: 64, cap: 32`, "distinct capability count exceeds the 32-bit bitmask width, truncating", with a `dropped` list of 32 names: `long_context, mcp, moderation, multimodal, music_generation, pdf_understanding, qa, realtime, realtime_audio, reasoning, reranking, research, retrieval, safety, speech_to_text, streaming, text_generation, text_to_speech, thinking_mode, tool_use, transcription, translation, tts, video_editing, video_generation, video_to_text, video_to_video, video_transcription, video_understanding, vision, visual_question_answering, web_search`.
2. `sab-candidate-index-worker`: "capacity error: metadata string blob overflow (raise SAB_CANDIDATE_METADATA_BLOB_BYTES)", "rebuild failed, keeping last-good generation". There was no last-good generation (first build), so `ACTIVE_GEN` stayed at -1.

Real catalog at the time: 112,140 active models (+5,108 disabled, never loaded), exactly 64 distinct legacy capability strings, `metadata` JSONB averaging 934 bytes (max 13,757; 100 MB summed over active rows). `capacity.ts` keeps `MAX_MODELS = 200,000` as the design ceiling.

### Bug 1: the "graceful" capability truncation was a silent correctness failure

Deviation 4 above chose to truncate the capability set to the first 32 sorted names instead of failing the rebuild, on the theory that the reader's fail-open rule for an unknown capability would absorb the loss. Two things made that wrong:

- The reader decodes a model's `capabilities` from the SAME truncated `capNames` list, so `reasoning`, `tool_use`, `vision`, `web_search`, `streaming`, `text_generation` and 26 other real capabilities were absent from every `Model` this path returned.
- `findModelsByRequirements` applies its own hard capability filter AFTER candidate retrieval, and that filter is fail-closed (`dynamic-model-selector.ts`, the `mapped.length === 0` branch). For any request requiring one of the dropped capabilities the index returned an over-inclusive pool (fail-open at the index level), the post-filter found no model carrying the capability, and the pool went empty. Thousands of models with `vision` in Postgres, zero eligible.

The test that "verified" the behavior (`encode-capacity.test.ts`, 40 synthetic capabilities) only asserted the reader level and never ran the decoded models through the selector's post-filter, which is why it passed. `MAX_CAPABILITIES` was also the only constant in `capacity.ts` whose doc claimed the encoder "fails the rebuild loudly (never silently drops capabilities)" while the code did the opposite.

### Bug 2: the metadata blob default was never multiplied against the catalog

`METADATA_BLOB_BYTES` defaulted to a flat 64 MiB (67,108,864 bytes), described as "sized generously above the id blob". The real requirement is rows x average metadata JSON size, plus the ~42-byte `lastSyncedAt` stamp `mapPrismaModel` folds into every row's metadata: 112,140 x ~976 = ~109 MB, 1.6x the default. The "Worker transient heap cost" section above had already recorded 96,118 rows x 982 bytes on 2026-09-10 (94 MB) without anyone comparing that product with the blob size. The encoder only discovered the overflow on the first row that no longer fit (around row 68,000), after encoding everything before it, and the error message did not say how much space was needed.

Every fixture in the test suite used 2 to 102 bytes of metadata per row (`memory-footprint.test.ts` encodes nothing at all; it only measures `computeLayout()`), so no test could have caught this.

### What coincided: the `ci_db` OOM incident

On the same day the `ci_db` container (1 GiB memory limit) had Postgres backends killed by the OOM killer seven times. The SAB worker's Postgres fallback (`prisma.model.findMany` over every non-disabled row, no `orderBy`, no `take`, no `statement_timeout` because the worker's pool is built from the raw `DATABASE_URL`) is exactly the kind of single-backend full-table read of a 2.1 GB relation that pressures that cgroup. With the Redis snapshot valid the worker did not run it during the canary, but it would have on any cold boot or snapshot expiry (18-minute TTL). The fleet-wide snapshot itself lives in `ci_redis-cache` (512 MiB) as a single string over 100 MB. Nothing in this change touches production; the flag stays `false` and must not be re-enabled while `ci_db` is unstable.

### Nothing in Prometheus showed any of this

A failed rebuild only set `state.lastError` and logged. `ci_sab_candidate_index_builds_total` counts successes, `_crashes_total` counts worker exits (a failed build is not a crash; the worker stays alive), `_ready` was 0 from `ensureSabCandidateIndexStarted()` onward. Every SAB metric read exactly like a process that had just booted, for the entire window, while the worker re-fetched the >100 MB snapshot and re-encoded it to the overflow point every 6 minutes. `getSabCandidateIndexStatus()` is not wired to any endpoint, and the `capabilitiesTruncated` field Precondition 3 referred to did not exist in it.

### What this change does

1. Capability mask: `CAPABILITY_MASK_WORDS = 4` (128 bits), row-major words in `schema.ts`, all bit arithmetic in one shared module (`capability-mask.ts`) used by both the encoder and the reader so the two halves cannot disagree; every comparison normalizes with `>>> 0` (bit 31 of each word is negative as an int32). More than 128 distinct capabilities is a hard `SabEncodeCapacityError` naming the count and the names that would have been dropped. `capabilitiesTruncated` is gone. The correctness matrix (`encode-reader-correctness.test.ts`) gained 12 cases on catalogs with 64 (the real list from the canary log) and 100 distinct capabilities, filtering on bits 32..99 and comparing byte for byte with `getFullCacheFairCandidateModels`.
2. Metadata blob: `METADATA_BLOB_BYTES` defaults to `MAX_MODELS x METADATA_BYTES_PER_MODEL` (200,000 x 1,024 = 195.31 MiB); `SAB_CANDIDATE_METADATA_BLOB_BYTES` still overrides. The encoder measures both string blobs before writing a byte and fails with the needed bytes, row count, average and capacity in the message. `capacity.ts` refuses at import any blob above the Int32 offset range. `encode-capacity.test.ts` now encodes the real shape (112,140 rows, exact 934-byte average with a 1-in-100 large tail up to 13,757 bytes, 64 capabilities): 104.8 MB, 51.2% of the default blob.
3. Failure surfacing: `ci_sab_candidate_index_build_failures_total{reason="capacity"|"fetch"|"other"}` (incremented on every `rebuild-failed`), `_distinct_capabilities`, `_metadata_blob_used_bytes`, `_metadata_blob_capacity_bytes`; `getSabCandidateIndexStatus()` exposes `buildFailures`, `lastFailureReason`, `distinctCapabilities`, `metadataBlobUsedBytes`, `metadataBlobCapacityBytes`. `_ready` stays 0 until a generation is actually published (unchanged, now tested hermetically in `manager-rebuild-failed-metrics.test.ts`).
4. Postgres fallback: keyset pagination on the primary key (`uid > last`, `orderBy uid`, `take` `SAB_CANDIDATE_WORKER_FETCH_PAGE_SIZE`, default 5,000) with `SET LOCAL statement_timeout` per page (`SAB_CANDIDATE_WORKER_STATEMENT_TIMEOUT_MS`, default 15,000), same `CATALOG_HOT_PATH_SELECT` allowlist plus `uid`, same `mapPrismaModel`, so the loaded data is identical. `uid > last` rather than Prisma `cursor:` because a cursor row deleted by discovery between pages would otherwise end the loop early with a silently partial generation. The Redis read is bounded (`SAB_CANDIDATE_WORKER_REDIS_TIMEOUT_MS`, default 10,000) because `redis-client.ts` never gives up reconnecting in production and an outage would have left `rebuildInFlight` stuck forever. `SAB_CANDIDATE_WORKER_POSTGRES_FALLBACK=false` disables the Postgres path entirely (default unchanged: enabled); production should consider setting it in a separate compose change while `ci_db` is memory-constrained. Redis remains the first source.
5. Memory cost corrected above (455.01 MiB virtual per replica).

### Preconditions added by this canary

- Precondition 1 now also requires `ci_sab_candidate_index_build_failures_total` to stay at 0 and `ci_sab_candidate_index_ready` to reach 1 within one rebuild interval of the flag turning on; a canary whose `ready` never leaves 0 is a failed canary regardless of what the logs say.
- Do not re-enable the flag while `ci_db` is under its 1 GiB limit and being OOM-killed. Even the paged fallback is extra read load on that instance.
- The real RSS delta per replica with the flag on (455 MiB virtual, roughly 2 x 145 MB resident at today's catalog, plus the worker's transient heap) has to be measured against the 4 GB container limit before a percentage rollout.
